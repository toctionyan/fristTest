# 统一语义与多任务规划边界合同

## 目的

防止“程序理解一部分语言、模型理解另一部分语言”，也防止“模型直接把自然语言拆成 Tool 调用”。

## 唯一语义职责

用户语言、跨轮关系、指代、多任务、纠正、暂停、恢复、取消、条件和顺序，由单一语义编译角色统一提出。程序只能提供权威事实并验证候选，不能根据关键词、枚举默认值、最近 Tool 或执行失败改写用户含义。

## 两阶段拆解

1. **业务 Goal 拆解**：生成用户可独立判断是否完成的业务效果；不依赖接口数量。
2. **执行计划展开**：读取 Capability Contract 后，将 Goal 展开为一个或多个 Tool/API/Interaction 步骤。

一个 Goal 可以对应一个 Tool、多 Tool 或事务链；多个 Goal 只有在一个复合 Capability 明确声明并证明全部效果时才可共用一个执行节点。

## 能力落地

- 能力索引只用于发现。
- 语义相似度只用于候选召回。
- 正式 MatchProof 必须比较稳定业务身份、对象类型、基数、权限、可用性和禁止替代规则。
- Goal 无精确能力时保留原 Goal，并返回 capability absent/forbidden/unavailable；不得改成相似能力。

## Oracle 与内部表示边界

- Oracle 验证用户可观察的业务效果、对象、条件、顺序约束和安全边界，不规定唯一 Goal AST。
- 禁止把精确 Goal 数量、Goal ID、`depends_on` 图、Tool 调用顺序或中文词面分类作为开放语义的唯一正确答案。
- Goal 之间的业务语义先决条件由语义 Owner 提出；Tool/handle/data 依赖由局部 Plan 单独表达，程序不得把后者反推为语言语义。
- 程序只可确定性验证引用存在、无自依赖、无循环、输入来源、权限、授权和事务顺序。
- 真实模型输出与 Oracle 内部结构不一致时，必须先进入 `oracle-review`；未证明用户效果错误前不得修改 Prompt 或运行时去迎合 Oracle。
- 同一用户效果存在多种安全且可执行的内部表示时，评测必须接受这些表示，或明确记录为何某种结构是业务/安全不变量而非实现偏好。

## 参数边界

- 用户语言参数：模型提出候选，必须绑定原文证据并通过 Schema。
- Target：模型提出对象候选，程序生成归属与来源证明。
- 系统参数：用户、租户、版本、Assessment、Draft、Grant、幂等和摘要只能来自权威系统。
- Tool 参数：固定 Adapter 从规范业务命令确定性生成，不允许模型临时拼接安全字段。

## 规划与验证

Planner 只为当前 Goal 展开局部计划。Plan Validator 必须证明：

- 每个 Goal 被覆盖或明确 unsupported；
- 每个步骤绑定精确 Capability；
- 每个 required input 有权威来源；
- 用户明确顺序被保留；
- 能力前置条件和事务顺序完整；
- 不存在循环依赖和危险并行写入；
- Attempt 不被当作 Receipt；
- 执行失败不会改变冻结 Goal。

Validator 只能接受、拒绝、阻断或要求输入，不得成为第二个语义 Planner。

## 失败裁决顺序

1. 先判断用户可观察效果是否遗漏、捏造或绑定了错误对象，以及安全、权限、数据来源或事务不变量是否被破坏。
2. 只有 Goal 数量、ID、依赖图或 Tool 顺序不同，而用户效果和不变量均成立时，必须裁决为 `ORACLE_DISPUTED`。
3. 只有证明真实用户效果或确定性不变量失败后，才能建立可写 Repair 基线；不得先修改 Prompt 或运行时再倒推理由。
